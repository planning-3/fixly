# fixly — 앱 리뷰·VOC를 팀 티켓으로

기획3팀 AX 팀프로젝트 프로토타입. 파일 하나(`index.html`)로 동작하는 웹 앱입니다. 브라우저로 열면 예시 데이터(무신사 공개 리뷰 500건)와 예시 VOC가 들어 있어 바로 써 볼 수 있습니다.

- 체험: GitHub Pages 주소(저장소 Settings → Pages에서 `main` / root로 켜면 `https://<계정>.github.io/fixly/`)
- 공개 리뷰·공개 자료로 만든 학습 프로젝트이며 무신사와 무관합니다.

## 폴더

| 경로 | 내용 |
|---|---|
| `index.html` | 실행 파일(= fixly VER9). 화면·동작·예시 데이터가 전부 이 안에 있음 |
| `docs/fixly-VER9.md` | VER8에서 바뀐 것, 이어서 고치는 법, 소스 전문(부록 B) |
| `docs/fixly-VER8.md` | VER8 명세(VOC 연동·AI 추천·팀 설정) |
| `docs/07_리서치_UX라이팅_오류_모니터링.md` | 이번 수정 작업의 근거(도구·가이드·오류 상황·모니터링 조사, fixly 코드 대조) |
| `TASKS.md` | 누가 무엇을 하는지, 브랜치 이름 |

## 같이 고치는 규칙 (파일 하나를 셋이 고치므로 꼭 지키기)

1. **작업마다 브랜치 하나.** `main`에서 직접 고치지 않습니다. 브랜치 이름은 `TASKS.md`에 적힌 것을 씁니다.
2. **시작 전에 최신으로.** 브랜치를 만들기 전에 `git pull`로 `main`을 최신으로 맞춥니다.
3. **작게 자주 커밋.** 한 기능이 끝날 때마다 커밋 메시지에 무엇을 고쳤는지 한 줄(예: `수집 상태 줄 추가`).
4. **올리기 전에 다시 합치기.** `git pull --rebase origin main` → 충돌이 나면 그 자리만 고치고 → `git push`. `--force`는 쓰지 않습니다.
5. **합치는 순서는 한 번에 하나.** Pull Request를 만들고, 다른 사람이 열어 보고 동작을 확인한 뒤 `main`에 합칩니다. 동시에 두 개를 합치지 않습니다.
6. **내 구역만.** 같은 함수를 두 사람이 동시에 고치면 충돌이 납니다. `TASKS.md`의 "고치는 곳"을 벗어나야 하면 먼저 말하고 고칩니다.
7. **데이터 모양을 바꾸면 버전도.** 티켓·리뷰·규칙 저장 구조를 바꾸면 `load()`의 `o.v===17`을 18로 올리고, 저장 키 `fixly_v9_`는 다음 버전에서 `fixly_v10_`으로 바꿉니다. 안 올리면 예전 브라우저 데이터로 화면이 깨집니다.
8. **합치기 전 확인 3가지.** 파일을 더블클릭해 열린다 / 티켓 카드가 열린다 / 콘솔(F12)에 빨간 오류가 없다.

## 코드에서 찾는 법

- VER9에서 고친 부분은 `/* VER9:` 주석으로 시작합니다. 이번 작업은 `/* VER10:` 으로 시작해 주세요.
- 주요 함수: 수집 `recollect()` · 저장 `load()`/`persist()` · 티켓 창 `ticketPanel()` · 통계 `statCard()`/`pct()` · 토스트 `toast()` · 분류 규칙 `firstMatch()`.
- 화면 문구는 `toast("…")`, `class="faint s"`(빈 상태), `placeholder="…"`, `new Error("…")`(파일 오류)로 검색하면 모입니다.

## 파일로만 열 때와 서버로 열 때

- 더블클릭(파일): 예시 데이터·예시 앱 3개·예시 메일함·첨부하기가 동작합니다.
- 실제 앱 주소 수집은 VER8의 `build/serve.js` 서버가 필요합니다(이 저장소에는 없음, `docs/fixly-VER8.md` 8~9장).
