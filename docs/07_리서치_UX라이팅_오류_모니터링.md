## 1. UX 라이팅 — 도구는 무엇이고, 가이드는 무엇을 요구하고, fixly 문구는 어디에 어긋나나

### 1-0. 멘토 조언과 실제 도구의 차이 [사실]

| "UX 라이팅 스킬을 돌려라" | **impeccable의 `clarify` 커맨드**가 유일하게 "UX copy, labels, error messages"를 직접 고치는 커맨드다 | hallmark·humanizer·REA는 UI 카피를 고치는 도구가 아니다 |

### 1-1. 도구 4개 상세 [사실, 각 README·SKILL.md·reference 파일]

**impeccable** (github.com/pbakaus/impeccable · Paul Bakaus · Apache 2.0 · 약 115k stars)
- 코딩 에이전트용 "디자인 어휘" 스킬. 이름 붙은 커맨드로 UI 작업을 조종·리뷰하고, LLM 없이 도는 62개 규칙 탐지기로 "AI slop"을 잡는다. Anthropic frontend-design 스킬에서 출발.
- 설치: 프로젝트 루트에서 `npx impeccable install` → 재시작 → `/impeccable init`, 또는 `/plugin marketplace add pbakaus/impeccable`, 또는 `npx skills add https://github.com/pbakaus/impeccable --skill impeccable`.
- 커맨드 24개: Steer(`bolder`/`quieter`/`distill`/`colorize`/`typeset`/`layout`/`animate`/`delight`/`overdrive`) · Review(**`critique`** = Nielsen 10 휴리스틱 0~4점 40점 만점·P0~P3, **`audit`** = 접근성·성능·테마·반응형) · Finish(`polish`, `harden`, **`clarify`**, `adapt`, `optimize`, `onboard`) · Live(`live`, `generate`) · Plan(`shape`, `init`→`PRODUCT.md`, `document`→`DESIGN.md`, `extract`).
- **`clarify`가 실제로 하는 것**: 개별 문자열이 아니라 **흐름 전체**를 감사(모호한 동사·명사, 전문용어, 막연한 상태 라벨, 결과/복구 단계 누락, 용어·대소문자 불일치, 중복 제목·확인창, 번역·폭에서 깨지는 문장, 긴급도 무시한 톤) → 상태별 메시지 위계(지금 필요한 사실 1개 → 다음 행동 → 맥락 → 톤) → 기능별 재작성(액션은 결과를 서술하는 동사+목적어, 파괴 액션은 대상+결과, 확인창보다 되돌리기, "OK/Submit" 금지 / 폼은 placeholder가 예시일 뿐이니 라벨 유지, 에러는 비난 없이 무엇을 어떻게 / 에러·권한은 무엇이 실패→알면 왜→복구, 내부 코드로 시작 금지, 농담 금지 / 빈 상태는 첫 사용·결과 없음·필터·권한·실패 구분 / 도움말은 컨트롤 설명 반복이 아니라 사용자의 암묵적 질문에 답하기 / i18n은 완전한 문장 단위) → **바꾸면 안 되는 것: 사실 주장·법적 의미·도메인 용어·브랜드 보이스(묻고 바꿈)**.
- 관리도구 규칙(`mode-operate.md`): 표준 컨트롤(버튼·탭·셀렉트·필터·정렬 헤더 테이블), 상태색(빨강=critical, 앰버=degraded)은 의미 있는 곳에만, **실제 제품명·현실적 데이터·단위·실제 라벨, placeholder 타일 금지**.
- 에러·빈 상태·i18n(`harden.md`): "Error occurred" 같은 일반 문구 금지, 상태코드별(400/401/403/404/429/500) 구체 처리, 에러 시 입력값 보존, 빈 목록·검색 결과마다 다음 행동, 로딩 문구는 무엇이 로딩되는지, 번역 확장 30~40% 여유, **CJK·이모지 테스트**.
- 빈 상태 5요소(`onboard.md`): 여기 무엇이 보일지 / 왜 중요한지 한 줄 / 시작 방법(CTA) / 아이콘 / 짧은 도움말.
- critique 루브릭의 카피 항목: H2 익숙한 용어, H4 일관된 용어, H5 오해 막는 라벨, H6 아이콘 라벨, H9 쉬운 말 에러("Email is missing @" > "Invalid input"), H10 간결·훑기 가능.
- 한계: 대비·작은 글자 검사는 렌더된 페이지 필요, live 모드는 CLI를 승인 없이 실행할 수 있음(낯선 저장소 주의), 컨텍스트를 많이 먹음(서드파티 리뷰). **한국어**: 언어별 규칙 없음, 예시 전부 영어, `harden`에 CJK 테스트만. 한국어 품질 [미확인].

**hallmark** (github.com/nutlope/hallmark · Together AI · MIT · 약 60k stars · v2.0)
- "AI가 만든 것처럼 보이지 않는" 웹 페이지 디자인 스킬. 재질 테마 50개, Floor/Reflex/Finish 품질 게이트, 브라우저 린터 `sloplint`.
- 설치: `npx skills add nutlope/hallmark -g`(`--agent claude-code`), 또는 `/plugin marketplace add nutlope/hallmark` → `/plugin install hallmark@hallmark`. Node 18+.
- 커맨드: `/hallmark <prompt>`(새 페이지), `/hallmark redesign <path>`(내용·연결 유지, 재디자인; "keep the layout"이면 스타일만, "polish"면 tells만), `/hallmark audit <path>`(수정 없이 리포트). 스크립트 `sloplint.mjs <file> --render`(8개 폭에서 린트, `--before`/`--kept`로 링크·필드·헤딩 유실 검사). **기존 디자인에는 사용자가 Hallmark를 명시해야만 동작.**
- **카피를 건드리지 않음**("Hallmark does not invent copy"). 텍스트 관련 게이트는 "AI 티" 금지에 한정: placeholder 이름("Jane Doe"), 스타트업 클리셰, 반박 어투("Not a feature. A platform."), 대시, 필러 도입부 / 지어낸 지표·후기 / 화면당 약 80단어 초과, 같은 사실 반복 / **템플릿 문장부호 — 가운뎃점 메타 문자열, "Learn more →" 화살표** / eyebrow 라벨, 자간 넓힌 대문자 라벨 / **"이미 눈에 보이는 효과에 축하 토스트" 금지** / 320~1920px에서 버튼·내비 라벨 줄바꿈 금지.
- 앱 화면 규칙(`flow.md`): "a screen someone works in rather than reads", 컨트롤 32~40px, 액센트 색은 주 액션·현재 선택·상태에만, 모달은 마지막 수단, **"tables before cards"**, **필터·탭·페이지네이션 상태는 URL에**, **데이터 영역마다 loading/empty/error/full 4상태 필수**(빈 상태="그것을 채우는 액션 하나", 에러="무엇이 깨졌고 무엇을 할지"), 파괴 액션은 undo 또는 confirm, 숫자는 제품에서(발명 금지), 통계는 tabular numerals 숫자+라벨만(아이콘 타일·그라데이션·안 잰 트렌드 화살표 금지).
- 차트 규칙(`data-viz.md`): 값 1개=stat tile, 2~5개=stat row 또는 가로 막대, 시계열=선, 7개 이상 범주=테이블, 부분/전체=누적 가로 막대, **파이·도넛·게이지 금지**, 인라인 SVG, 막대 ≤24px·0 기준선, 선 2px, **y축 하나**, 그림자·3D·그라데이션 금지, "Text never wears the data colour", "A fabricated series is worse than an empty slot", 대시보드는 hero stat 1 + 보조 차트 1 + 테이블 1.
- 한계: `sloplint --render`는 puppeteer+Chrome 필요, 마케팅 페이지 지향. **한국어**: 언급 없음, 클리셰 목록은 영어 기준 [미확인].

**humanizer** (github.com/blader/humanizer · MIT · v4.0 · 약 73k stars)
- Wikipedia "Signs of AI writing" 기반으로 AI 티를 지우되 의미는 유지. AI 탐지기 회피용 아님("detectors still flag most of its output").
- 설치: `/plugin marketplace add blader/humanizer` → `/plugin install humanizer@humanizer`, 또는 `npx skills add blader/humanizer --global`. 호출 `/humanizer <텍스트>` 또는 파일 경로(산문만 고치고 코드·명령·경로·데이터는 보존), 자기 글 2~3단락을 샘플로 주면 목소리 매칭.
- 워크플로: 강한 패턴 표시 → 초안(사실·이름·숫자·날짜 보존) → 자주 남는 tell 재검사 → 최종. **비격식·짧은 글(채팅·댓글)은 tell이 2개 이상 겹치지 않으면 손대지 않음.**
- 패턴 26개, 6군: A 서술 대신 연출("not X but Y", 극적 조각문, 격언, "Let's dive in", 없는 반론) · B 규칙 리듬(억지 3항 나열, 같은 시작 반복, 대시 연결, 수식어 쌓기, 피동·주어 생략) · C 과장·빌린 권위(AI 상용어 "crucial, delve, showcase, testament", 의의 부풀리기, 막연한 연관, 광고 어투, 익명 전문가, is/has 회피) · D 서식(장식 볼드, Title Case·이모지·화살표 제목, 곡선 따옴표) · E 챗봇 잔재(인사·제안·맺음말, 면책, 제목 반복, 문서 자체 서술) · F 독자가 아는 맥락 재설명.
- **한국어**: 비영어 지원 언급 없음. 8(대시)·10(하이픈)·12(영어 어휘)·15(-ing)·18(is/has)·21(따옴표)은 영어 전용. 대안: `NomaDamas/k-skill` **korean-humanizer**(번역체·AI 상투어·과도한 명사화·피동·3의 법칙·마무리 상투구 등 A~J 60+ 패턴, S1~S3 심각도, 변경률 가드 30%/50%, 한국어 전용 패턴 예 "그/그녀 과용, 이중 조사, 연결어미 뒤 쉼표, **경어 불일치**"), `daleseo/korean-skills` **humanizer**(40패턴, KatFishNet 논문 arXiv 2503.00032 기반).
- fixly에 쓸 때의 현실: **버튼·토스트·2~3어절 라벨에는 패턴이 거의 안 걸린다.** 쓸모 있는 곳은 온보딩 안내, 도움말 단락, 빈 상태 설명 같은 2문장 이상 산문.

**REA / 역공학**
- 가장 유력한 후보 `morluto/rea` "Reverse Engineer Anything": 바이너리·JS/Electron 앱·.NET·웹사이트·APK·펌웨어를 분석해 의사코드·모듈 관계를 돌려주는 MCP. MIT, 약 475k stars. `npx rea-agents setup`. **UI·디자인·카피는 README 어디에도 없다.** 짝퉁 저장소 주의 문구 있음.

### 1-2. Shopify Polaris 콘텐츠 가이드 — 규칙 체크리스트 [사실, GitHub 저장소 main·v12 태그 + shopify.dev]

**에러 메시지**
- 무엇이 잘못됐고 무엇을 해야 하는지. 정확한 숫자·날짜로 구체적으로. 구조: 제목(선택, 영향) + 본문(고치는 법) + CTA(원클릭 해결).
- "invalid" 금지(필요하면 "not valid"). "Error", "An error occurred", "1 error" 같은 일반 문구 금지. 과도한 사과·과장·기술용어·농담·"걱정 마세요" 금지, 질문형 금지.
  - Don't "Today's sales data might not be accurate, but please don't worry—it's just temporary." / Do "Some of today's sales data isn't updated yet. This will be fixed soon. Your data is safe…"
- "we/us"는 Shopify가 원인일 때만. 검증 배너 제목은 **지시형+콜론**("To save this product, make 2 changes:"), 에러 개수만 적지 않기("There are 2 errors on this page" ✗). 목록 항목은 **필드 라벨로 시작하고 고칠 방법**("Add a discount code" > "Discount can't be blank").
- 필드 검증 메시지는 2~3단어, 배너 본문은 2문장 이하, 행동 언어. 빈 필드는 검증하지 않고 포커스가 떠난 뒤 필드 아래에. 검증 중 입력값을 지우지 않음.
- **토스트로 에러 금지**(3초 뒤 사라짐). 예외: 연결 끊김처럼 사용자 탓이 아닌 에러. **모달로 에러 금지.**
- 페이지 전체 에러: 가장 유력한 해결책(새로고침·이전·홈). 해결책 없는 에러: "Something went wrong. Refresh your browser to try again."(Don't "Sorry, something went wrong. Learn more."). 빨강은 사업에 해가 되는 critical에만, 노랑은 일상 경고.
- 인라인 에러는 1문장, **비난을 피하기 위해 피동**("Store name is required" / Don't "You didn't enter a store name").

**행동 언어(버튼·링크·확인창)** (v12 actionable-language)
- 제목은 sentence case 한 문장, 문장부호 없음. 지시문은 **명령형 동사로 시작**, "you can" 금지.
- **버튼 = 강한 동사 + 명사**(예외 Done, Close, Cancel, OK). "Activate Apple Pay" / Don't "Try Apple Pay", "Settings". 결과를 잘못 예고하지 않기.
- 링크: "click here" 금지, 문장 밖 링크는 동사+명사, "Learn more"는 **화면당 1개**.
- 확인창: 되돌릴 수 없는 액션에만, 과제 1개, 본문 1줄, CTA 최대 2개. 제목은 **동사+명사 질문**("Discard unsaved changes?", "Delete 2 collections?" / Don't "Are you sure you want to delete?"). 본문은 "Are you sure?"로 시작 금지, 되돌릴 수 있는지 1줄("This can't be undone.").
- 삭제는 "Delete"/"Cancel", 변경 폐기는 "Discard"/"Keep editing", 이탈은 "Leave page"/"Stay". Save(즉시 저장) vs Done(지연 저장). **"OK"는 액션이 아님 → 읽었음은 "Close", 동의는 "Accept"**. Create(새로 만듦) vs Add(기존 것 추가), Select(정해진 목록) vs Choose(열린 결정), Edit(값 1개) vs Manage(여러 액션), Export(형식 변환) vs Download(동일 형식). 방향 표현(above/below) 금지.

**기본 원칙(fundamentals)**
- 단어 하나하나가 노이즈. 아이콘이 의미를 맡으면 글자 삭제. "헤더+subcopy+버튼이 버튼 하나로 줄어드나?" 시험. **한 문장이면 끝 문장부호 생략.** 축약형 사용, 전문용어는 실제 사용자가 쓰는 것만, 7학년 읽기 수준, **소리 내어 읽어 사람이 그렇게 말하지 않으면 다시 쓰기**. 동사로 시작("add apps" > "you can add apps").

**보이스·톤** (shopify.dev)
- 사용자 감정을 단정하지 않기. Real / Proactive / Dynamic("every, all, most" 일반화 금지) / Guide.
- 일상 작업: 아이콘으로 충분하면 글자 생략, 동일 액션은 동일 라벨, **필러·말줄임표("Add a note…") 금지**. 단순 에러: "fatal, forbidden, invalid" 같은 극적 단어 금지, 에러 코드는 해결에 도움될 때만. 완료 인정: "Product saved" 수준의 소박한 확인, **단순 작업을 "success"라 부르지 않기**, 사용자가 신날 거라 가정하지 않기. 축하는 가장 드물게(1주년 수준).

**알림 패턴** (shopify.dev alerts)
- 시스템 알림(연결 끊김·구독 만료)=배너 / 작업 알림(제출 성공·입력 오류)=토스트 또는 인라인.
- **토스트: 3단어 이하, 성공 전용**, 액션 없으면 자동 소멸. Do "Image deleted"+Undo / Don't 빨간 "Server error" 토스트. 성공 배너는 지연·지속·CTA 있을 때만.
- 인라인 에러는 필드 아래 빨간 글자, 입력 중에는 띄우지 않음. 리스트 안 경고는 배지+아이콘(색만으로 전달 금지). 에러 배너: 무엇이 일어났고 다음 길. Don't "Oops, we did it again." 공포 어휘·유머·번역 안 되는 관용구 금지.

**컴포넌트별**
- Toast(v12): **명사+동사 패턴**, 짧고 긍정형. Do "Product updated", "Connection timed out" / Don't "No internet connection", "Your product has been successfully updated", "We were unable to save the customer". 액션은 동사 1개("Undo, Retry"), **"OK, Got it, Cancel, Dismiss" 금지**(X가 닫기). 기본 5초, 액션 있으면 10초.
- Empty state: 제목은 행동 지향 Do "Create orders and send invoices" / Don't "Orders and invoices"; 주 액션 1개 동사+명사; **기능을 안 써서 실패한 듯·죄책감 느끼게 하지 않기**.
- Banner: 주제 1개, 1~2문장, 제목 반복 금지, 경고·critical은 해결 방법 포함. 링크 텍스트는 목적지 이름과 일치. 마케팅용 배너 금지.

**문법·표기**
- Sentence case 전부. 축약형. 볼드는 의심되면 쓰지 않기. **제목에 느낌표 금지**, 느낌표는 페이지당 1개 이하. 물음표는 결과를 모를 때만.
- 숫자는 아라비아("5 orders"), 4자리 이상 쉼표, 범위는 en dash, 상한 없는 범위는 "or more". 날짜는 월 이름(December 11, 2024), 숫자만(12/11/24)·서수 금지. 상대 시간: "Just now" / "13 minutes ago" / 오늘 "10:30 am" / "Yesterday at 10:30 am" / 7일 내 "Friday at 10:30 am" / 1년 내 "Aug 14 at 10:30 am".
- 사용자는 항상 "you"("My Profile" 금지), 앰퍼샌드 금지, **말줄임표는 placeholder·여운에 금지**("Search files" / Don't "Start typing to search for files…"), 마침표는 단일 문장 UI 카피에 없음·2문장 이상이면 있음. 메뉴 액션은 동사+명사.

**도움말·네이밍·포용**
- Help content: 자주 쓰는 영역은 도움말 최소, **"Help content belongs as close as possible to the part of the UI it references"**, 도움말로 기능 홍보 금지. Help documentation: Fail fast(요건 미충족을 단계 전에), 항상 다음 단계, "faster, better, easier" 근거 없이 금지, "find/locate" 금지, "If…, then…".
- Naming: 기능은 설명형 소문자 이름, 약어 새로 만들지 않기, 첫 사용 시 풀어 쓰기, 아이콘은 기능으로 이름("Add image" / Don't "Image").
- Inclusive: "disable" 대신 "turn off/inactive", **"easy, simple, quick, just, only" 금지**("Just put in your email" → "Enter your email address and password"), blocklist/allowlist, main/primary, they/them.
- Product content: 사람들이 실제 쓰는 단어 조사, **중요 명사·동사 목록을 만들고 동의어 제거(개념 하나=단어 하나)**.

### 1-3. Atlassian Design System 콘텐츠 가이드 — 규칙 체크리스트 [사실, atlassian.design/foundations/content/*]

**에러 메시지**
- 에러는 **행동 뒤**, 경고는 **행동 전**. 컴포넌트: Flag, Inline message, Modal, Section message(배너는 에러 목록에 없음).
- 제목(선택): 그것만 읽어도 무슨 일인지, **3~4단어**, sentence case, **제목에서 해결법 말하지 않기**, 본문에서 제목 반복 금지. 본문: 무엇이 일어났고·무슨 뜻이고·무엇을 할지, **1~2문장**. 원인 모르면 **지어내지 말고** "something went wrong"+다음 단계. 기술 세부 금지.
- CTA: 결과를 서술하는 명령형 동사, 1~2단어, **"OK" 금지**, 닫기/취소 제공.
- 톤: 명료(과장·경보 어투 금지) / 공감(비난·파국 금지) / 해결 지향 / 관점(**제품 역할은 "we", 사람을 문제에 묶는 "you" 금지**) / **"please" 금지(필수 단계가 선택처럼 들림), "sorry" 금지(에러가 더 심각해 보임)** — 되돌릴 수 없는 심각한 결과에만 예외.
- 원인·해결책이 여럿이면 가장 유력한 원인·가장 쉬운 해결을 첫 문장에, 백업(지원 문의)은 둘째 문장.

**성공·경고·정보**
- Success: 제목 3~4단어, **"Success"·"successfully" 금지**, 느낌표 금지. Do "Page published" / Don't "Success! Your page was successfully published." 결과 확인+보기 링크, 1~2문장. **자주 뜨는 메시지는 더 짧고 덜 장난스럽게**.
- Warning: 행동 전. Do "Your bill may increase" / Don't "Time to pay up!". 이유·잠재 문제·할 일·안 하면 생기는 일. **비난 회피: "We're running into some difficulties" > "You've lost connection"**. 유머 금지. 위험 행동 확인은 진행·취소 둘 다, 되돌릴 수 있는지 명시.
- Info: 행동을 요구하지 않음, 바로 요점. 빈 상태는 이유 설명+다음 단계.
- 유형↔컴포넌트: 배너는 **시스템 수준 critical만**, 플래그는 최소 상호작용 확인용, 모달은 짧은 필수 과제, 스포트라이트는 기능 발견.

**빈 상태**
- 제목만 필수: 현재 상태 요약, 질문 아니면 끝 문장부호 없음. 설명(선택): 왜 비었는지+다음에 어디로, 1~2문장, 전문용어 금지, 제목 반복 금지. 액션(선택): 명령형 동사 1~2단어, "OK" 금지, 주 버튼 1개.
- 톤: 첫 사용=영감·교육, 과제 완료=축하, 결과 없음=중립+다음 단계. **자주 뜨는 것(알림 비움 등)은 짧고 덜 장난스럽게.**

**스타일·문법·문장부호**
- sentence case, **버튼·라벨·액션 제목에서 관사 생략("Create password")**, 제목은 **동사로 시작**, 제목에 물음표·볼드·마침표·콜론 금지, **UI에서 -ing형 금지("Add a page" / Don't "Adding a page…")**.
- "e.g., i.e., etc., &" 금지. 축약형, 능동태, **지시·메시지는 현재 시제, 완료된 행동(에러 제목·성공 플래그)은 과거 시제 "Upload failed"**.
- 숫자 아라비아, **범위는 "to"("rows 1 to 4")**, "Step 1 of 2"("1/2" 금지). 목록 6개 이하. 느낌표 UI 금지. 마침표는 완전 문장 메시지에만(헤더·툴팁·필드 설명·메뉴명 금지).
- **잘림 회피**: 줄이거나 줄바꿈, 여러 폭·확대율에서 테스트, 불가피하면 전체 텍스트 툴팁. 단계 설명에서 ">" 대신 "then"(스크린리더가 "greater than"으로 읽음).

**보이스·톤**
- Bold(불안·혼란·분노 상태에는 톤 다운하고 더 지시적으로) / Optimistic(지금 가장 중요한 정보, 일관된 어휘) / **Practical, with a wink(UI에서는 wink를 가려 쓰고, 마감·에러·신규 사용자에게는 금지)**.
- 6원칙 중: **기대 충족(직접 도움이 필요한 순간엔 영감·즐거움 시도 금지)**, 뜻밖의 즐거움은 신뢰 쌓인 뒤 작은 장식 수준, **유머·건방을 delight로 쓰지 않기**, "Once may amuse, but a dozen times may annoy".

**포용적 글쓰기**
- **"easy", "simple" 같은 난이도 판단 금지**, 은유·관용구·전문용어 금지. they/them. "disabled"는 "turned off/unavailable". **링크·라벨은 서술적("Learn more" 금지 → "About Rovo")**, "Step 1" → "Create project (step 1 of 3)".

**날짜·시간**
- 하드코딩 금지, 로케일 포맷. 숫자만 날짜(10-8-2026)는 국가별로 뒤바뀌므로 회피, 저장·정렬·내보내기는 ISO 8601. 상대 시간: just now / a minute ago / x minutes ago / 1 hour ago / yesterday / x days ago(2~6일) / 1 week ago / 7일 초과는 날짜. **항상 툴팁으로 정확한 시각 제공**. "fortnightly, bi-" 금지.

### 1-4. 그 밖의 공개 가이드(각 5규칙) [사실]

- **Microsoft Writing Style Guide**: "warm and relaxed, crisp and clear, ready to lend a hand". ① "Write like you speak": "Invalid ID" → "You need an ID that looks like this: someone@example.com" ② 입력 방식 중립 동사 — click/tap 금지, "Select"·"Enter"·"Go to"·"Open"·"Turn on"·"Clear" ③ 제목·UI 타이틀에 마침표·콜론 금지, "When in doubt, don't capitalize" ④ 동사로 시작, "you can"·"there is/are" 제거 ⑤ 에러는 사용자 비난 금지·앱이 책임: Do "We couldn't upload the picture. If this happens again, try restarting the app." 버튼은 1~2단어, 다이얼로그 제목(질문)과 버튼(답)은 호응.
- **Mailchimp Content Style Guide**(CC BY-NC 4.0): ① "clarity matters more than entertainment", 억지 유머는 없는 것보다 나쁨 ② 버튼은 동사 포함·간결 ③ 폼은 최대한 짧게 ④ 링크 텍스트에 "Click here" 금지 ⑤ 번역 대비: 능동태·주어-동사-목적어, -ing 회피, 다의어 회피, **동의어 금지(용어 하나로 통일)**.
- **Google Material(M2)**: ① 짧고 직접: Do "Save changes?" / Don't "Would you like to save your changes?" ② 2인칭 기본, **한 구절에 1·2인칭 혼용 금지** ③ 제품 동작은 현재 시제 "Message sent"(Don't "has been sent") ④ 라벨 뒤 콜론 금지("Share with" / Don't "Share with:"), 단독 문장에 마침표 생략 ⑤ 기술 용어 회피, 의무 강요 대신 과제에 집중("Register to vote" / Don't "You must register before you can vote").

### 1-5. 한국어 관리도구 카피에 적용하기 [해석·제안]

**그대로 옮겨도 되는 규칙(구조 규칙)**
- 에러 = **무엇이 일어났나 + 어떻게 고치나**(+알 때만 왜). 코드·"오류가 발생했습니다" 같은 빈 문구 금지. 원인 모르면 지어내지 않기.
- 제목 3~4어절, 본문 1~2문장, 제목을 본문에서 반복하지 않기, 제목에서 해결법 말하지 않기.
- 버튼 = **결과를 예측할 수 있는 구체 동사(+목적어)**, "확인" 같은 빈 라벨 금지, 확인창 버튼은 제목의 질문에 답이 되게, 삭제는 "삭제"/"취소"로 고정, 되돌릴 수 있는지 1줄.
- **토스트 = 성공 전용, 2~3어절, 명사+결과형**, 에러는 토스트에 넣지 않기(연결 끊김 예외), 액션은 되돌리기 하나.
- **빈 상태 = 상태 요약 제목 + 왜 비었는지/다음에 할 일 1~2문장 + 채우는 액션 1개**, 첫 사용·결과 없음·필터·권한·에러 구분, 자주 뜨는 것은 더 짧게.
- 성공 메시지에 "성공적으로" 금지, 느낌표 금지, 일상 작업 축하 금지.
- 개념 하나 = 단어 하나(용어집), 같은 액션은 같은 라벨.
- 숫자는 아라비아, 천 단위 쉼표, 상대 시간("방금, 3분 전, 어제 10:30")에는 정확 시각 툴팁.
- "쉽게, 간단히, 그냥" 같은 난이도 판단 금지, 은유·유머는 에러 상황에서 금지.
- 도움말은 설명 대상 바로 옆에, "더 알아보기"는 화면당 1개.
- 입력 중 검증 금지, 빈 필드는 검증하지 않음, 에러 시 입력값 보존.

**한국어에 맞게 바꿔야 하는 규칙**
- **Sentence case·관사·축약형(can't)**: 대응 개념 없음. 영어 용어(VOC, CSV, API)는 영어 표기 통일. "축약형=친근함"의 대응은 **어미 선택**.
- **어미(해요체 vs 합니다체)**: 토스는 제품 텍스트 전부 해요체, 과한 존대("~하시겠어요?", "~드립니다")를 깎고, 부정형보다 긍정형(토스 디자인 가이드·UX 라이터 인터뷰). B2B 관리도구는 합니다체도 흔함. **중요한 건 하나로 고정하고 한 화면 안에서 섞지 않는 것**(korean-humanizer E-7 "경어 불일치"). 권장: 메시지·도움말은 한 어미, **버튼·메뉴·테이블 헤더·태그는 명사형("저장", "티켓 만들기")**, 요청은 "~해 주세요", 안내는 "~하세요".
- **"please/sorry" 금지**: 한국어 "~해 주세요"는 중립적이라 그대로 금지하면 어색. 옮기면 "**죄송합니다**로 시작하는 에러 금지, '~해 주시기 바랍니다/부탁드립니다' 같은 격식 과잉 금지".
- **피동태**: Polaris는 인라인 에러에서 비난 회피용 피동을 권하고, 한국어 humanizer들은 과한 피동·명사화를 AI 티로 잡음. 절충: **에러 귀인 문장만 주어 없는 서술("매장 이름이 필요해요", "저장되지 않았어요")**, 지시문은 능동·명령형.
- **"you can" 제거** = 한국어 "~할 수 있습니다/있어요" 남용과 대응. 지시문은 "~하세요/~해 보세요".
- **-ing형 금지** = "~하기 / ~중" 구분. 제목·버튼은 "티켓 만들기", 진행 상태는 "불러오는 중"처럼 상태에만.
- **토스트 noun+verb** = "티켓 저장됨"(명사+됨) 또는 "티켓을 저장했어요"(해요체) 중 하나로 통일. 두 버튼이면 보조 버튼은 "닫기"(읽기 끝)와 "취소"(변경 폐기)를 구분.
- **영어 혼용 용어(VOC, 이슈, 티켓, CSV)**: 설명형 한국어 우선, 업계에서 실제 쓰는 영어만 유지, 첫 등장 시 풀어 쓰기("VOC(고객 의견)").
- **길이·줄바꿈**: 어미가 붙은 버튼("불러오는 중입니다")은 길어짐 → 320~1920px 줄바꿈 금지(hallmark 49a), CJK 테스트(impeccable harden).
- **날짜**: 한국 관리도구는 "2026.11.24" 또는 "2026-11-24" 관행 → Polaris의 "December 11, 2024"는 적용 안 함, Atlassian의 ISO 8601·상대 시간 표+정확 시각 툴팁 채택.

**하루 안에 UI 문자열 ~130개를 점검하는 절차**
1. (1시간) 문자열 추출 표: ID / 위치 / 유형(버튼·토스트·빈 상태·에러·도움말·헤더·필터) / 현재 문구 / 트리거. → **1-6에 이미 뽑아 둠(131개).**

3. (3시간) `/impeccable critique fixly-VER9.html` 사전 점수 저장 → `/impeccable clarify`를 **유형별로 나눠**("errors only", "empty states only", "toasts and confirmations only", "help text only") **"코드를 고치지 말고 before/after 표로 제안만"** 지시, 규칙 파일을 읽게 하고 한국어 예시 2~3개 제공 → `/impeccable harden`은 빈 상태 5유형·상태코드별 에러가 **빠진 곳** 찾기 용도 → (선택) `/hallmark audit`은 AI 티(화살표, 축하 토스트, 4상태 누락) 점검, **redesign 금지** → humanizer는 2문장 이상 산문에만, 한국어는 `daleseo/korean-skills humanizer` 또는 `korean-humanizer`.

### 1-6. fixly 문구 131개 대조 [코드 + 위 규칙]

VER9 코드에서 사용자에게 보이는 문자열을 전부 뽑았다(예시 데이터 제외): 버튼 57 · 토스트 26 · 입력칸 안내 20 · 빈 상태 7 · 오류 6 · 안내 6 · 말풍선 6 · 확인 창 3. 원본 표는 `scratchpad`의 `fixly_copy_inventory.tsv`.

**이미 잘 맞는 것**
- 금지어 없음: "성공적으로" 0건, "죄송" 0건, "오류가 발생" 0건, 느낌표 0건, "쉽게/간단히" 0건.
- 어미는 해요체로 거의 통일("~했어요", "~해 주세요"). 버튼은 대부분 명사형("저장", "삭제", "등록", "닫기", "안건으로 올리기", "티켓으로 결정").
- 빈 상태 대부분이 "왜 비었나 + 다음 행동" 꼴: "아직 회의록이 없어요 · 안건 탭에서 등록해요", "아직 처리한 비슷한 티켓이 없어요 · 이 티켓을 완료하고 처리 내용을 댓글로 남기면 다음 비슷한 건에 안내돼요".
- 파일 오류는 "무엇 + 어떻게" 공식에 맞음: "'내용' 칸이 있는 줄을 찾지 못했어요. 양식을 내려받아 써 주세요", "이 브라우저는 엑셀을 읽지 못해요. CSV로 저장해 첨부해 주세요".
- 입력칸 안내는 예시형("예: 윤가람", "예: 겨울 기획전 배너 교체") — Polaris "placeholder는 예시" 원칙에 맞음.
- 확인 창 버튼은 "바꾸기"/"취소"로 질문에 답하는 구조.

## 2. 오류 상황 — 리뷰 수집이 멈추면? 통계가 깨지면?

### 2-0. 두 질문에 대한 짧은 답

**(a) 리뷰 수집이 멈추면?**
- fixly가 쓰는 두 수집 경로는 모두 **비공식**이다. Google Play는 `google-play-scraper`(Node·Python)가 Play 웹의 내부 `batchexecute` 응답을 파싱하는 구조라 Google이 화면·payload를 바꾸면 그날 깨진다. Node README가 직접 "parser may break when Google Play's layout changes"라고 쓰고, 유지보수자도 "no longer actively maintains"라고 밝힌다 [사실]. Apple RSS(`itunes.apple.com/{cc}/rss/customerreviews/…`)는 Apple 문서가 없는 레거시 엔드포인트다(개발자 포럼에 쿼터 질문이 올라왔으나 답변 0건) [사실].
- 실제 장애 이력을 보면 **"멈춘다"보다 "조용히 줄어든다"가 더 흔하다.** Python 라이브러리는 모든 예외를 `except Exception: token=None; break`로 삼켜서 네트워크 실패·파싱 실패·429가 전부 "리뷰가 더 없음"과 같은 모양으로 돌아온다. 2024년 2~4월에는 Google이 HTTP 200 안에 `PlayGatewayError`를 넣어 보내면서 전체 리뷰의 5%만 수집되는 사태가 있었고(이슈 #209, 댓글 59개, 아직 open), 라이브러리 수정 없이 사용자 monkey-patch로 버텼다 [사실].
- 그래서 현장 대응의 핵심은 셋이다. ① **"0건 수집"과 "실패"를 구분**하는 상태(성공/부분 성공/실패)와 `last_successful_run` 시각 기록 ② **지수 백오프 + 지터 재시도**, 한도 초과 시 **서킷 브레이커**로 잠시 멈추기 ③ **수동 CSV 가져오기 같은 우회 경로**(Play Console 월별 리뷰 CSV, App Store Connect API)를 항상 열어 두기. 사용자에게는 "마지막 동기화 n시간 전 · 상태 지연 · 원인 스토어 응답 제한"처럼 **시간·상태·원인**을 한 줄로 보여 주는 것이 Appbot·AppFollow가 쓰는 방식이다(2-5).

**(b) 통계가 깨지면?**
- localStorage 단일 파일 구조에서 통계가 깨지는 경로는 대부분 **데이터층**에 있다. 용량 초과(`QuotaExceededError`, origin당 약 5MiB), 손상된 JSON(`JSON.parse` → `SyntaxError`), 스키마 버전 불일치, 그리고 계산층의 `0/0 → NaN`, 타임존 버킷 오류, `toFixed` 반올림 [사실].
- 현장 패턴은 ① 저장 전 `storageAvailable()` 점검과 `try/catch` ② 상태에 `schemaVersion`을 두고 `migrate()` 함수 체인으로 올리기, 마이그레이션 전 백업 ③ 통계 함수는 **분모 0·빈 기간·NaN을 "데이터 없음"으로 명시 반환**하고 차트는 빈 상태 화면 따로 ④ 날짜 버킷은 타임존 하나로 고정 ⑤ CSV는 UTF-8 BOM. 사용자에게는 "통계를 계산할 수 없습니다 · 백업에서 복원 / 초기화"처럼 **복구 선택지**를 같이 보여 준다.

| S1 | **localStorage 용량 초과** | `setItem`에서 `QuotaExceededError`, 데이터 유실. origin당 **5MiB**(Web Storage 전체 10MiB), 문자열만. 리뷰 1건 ≈ 0.5~1KB면 5천~1만 건에서 임계. 감지: `setItem` try/catch, 저장 전 `JSON.stringify(state).length`로 용량 추정, `navigator.storage.estimate()`. 처리: 원본 raw 삭제 → 오래된 리뷰 압축 → IndexedDB 이전. 문구: "브라우저 저장 공간(5MB)이 가득 찼습니다 · 오래된 원본을 정리하거나 내보내기 후 비우세요" |
| S2 | **저장소 사용 불가·삭제** | 사생활 보호 모드면 quota 0. Safari는 7일간 상호작용 없으면 script 저장 데이터 삭제. 브라우저 LRU 삭제. 처리: 시작 시 MDN `storageAvailable()`(QuotaExceededError이면서 `storage.length !== 0`일 때만 사용 가능으로), 불가 시 메모리 모드 + 내보내기 유도, `navigator.storage.persist()` 요청. 문구: "이 브라우저에서는 데이터가 저장되지 않습니다 · 작업 후 JSON으로 내보내세요" |
| S3 | **JSON 손상** | `JSON.parse` → `SyntaxError`. 원인: 저장 중 탭 종료, 용량 초과로 절반만 기록, 두 탭 동시 쓰기. 처리: 로드 try/catch → `backup` 키(마지막 정상본)에서 복원 → 없으면 빈 상태로 시작하되 손상본을 `corrupt_<ts>` 키로 보존. 쓰기는 "backup ← current, current ← new" 2단계. 문구: "저장 데이터를 읽을 수 없어 11-23 18:00 백업으로 복원했습니다" |
| S4 | **스키마/버전 불일치** | 새 코드가 옛 데이터를 읽어 `undefined` 전파 → 통계 NaN. 처리: 상태에 `schemaVersion`, 로드 시 `migrations[v](state)`를 저장 버전+1부터 순차 적용(redux-persist `createMigrate` 방식), 마이그레이션 전 백업, **저장 버전이 코드보다 높으면 쓰기 금지 + 경고**. 분류 규칙 변경은 `classifierVersion`을 티켓에 기록해 재분류 가능하게. 문구: "데이터 형식을 v17→v18로 업데이트했습니다(백업 보관)" |
| S5 | **0 나누기 / NaN** | 리뷰 0건 기간의 비율, `sum/0` → NaN, "NaN is contagious"라 이후 집계가 전부 NaN. 감지: `Number.isNaN()`(전역 `isNaN`과 다름), `Number.isFinite()`. 처리: 분모 0이면 `null` → UI "—"/"데이터 없음", 차트는 `null`(Chart.js "null can be used for skipped values") |
| S6 | **빈 기간 차트** | 리뷰 없는 주가 통째로 빠져 x축이 건너뜀 → 추세 왜곡. 처리: 기간 축을 먼저 만들어 0/null로 채운 뒤 데이터 join, 전체 0건이면 빈 상태 카드 |
| S7 | **타임존 버킷** | Apple RSS `-07:00`, ASC API `-08:00`, Python naive local, Node UTC `Z`가 섞임. `new Date(str).getDate()`는 **브라우저 타임존**으로 계산해 KST 사용자는 날짜가 밀릴 수 있음. 처리: 저장 UTC ISO(`toISOString()`), 버킷은 `Intl.DateTimeFormat('ko-KR',{timeZone:'Asia/Seoul'})`로 고정, 차트에 "KST 기준" 표기 |
| S8 | **퍼센트 반올림** | `(2.55).toFixed(1) === '2.5'`, 비율 합이 99.9/100.1%, `toFixed`는 문자열 반환. 처리: 정수(건수)로 계산하고 표시 직전에만 반올림, 합 100% 보정 규칙 명시 |
| S9 | **CSV 인코딩** | UTF-8 CSV를 Excel이 ANSI로 열어 한글 깨짐. SheetJS: "csv output will always include the UTF-8 byte order mark"(단 `sheet_to_csv()` 문자열은 BOM 없음). 처리: Blob 앞 `﻿`, 셀 안 줄바꿈·쉼표·따옴표 escape, **수식 주입 방지**(`=`,`+`,`-`,`@`로 시작하는 리뷰 본문 앞에 `'`) |
| S10 | **XLSX 생성** | 큰 문자열 `Invalid string length`, 메모리 초과, 압축 기본 off로 파일 비대, 날짜가 숫자 serial, 15자리 유효숫자. 처리: 내보내기는 Web Worker, 날짜는 ISO 문자열 열, 10만 행 이상이면 CSV로 |
| S11 | **다중 탭 경쟁 쓰기** | 두 탭이 각자 읽고 저장 → 나중 저장이 덮음. `storage` 이벤트는 다른 탭에서만 발생. 처리: 쓰기 전 `updatedAt` 비교(낙관적 잠금), 이벤트 수신 시 재로드, 또는 "다른 탭에서 변경됨 · 새로고침" 배너 |

### 2-5. 상용 도구가 수집 문제를 사용자에게 알리는 방식 [사실, 헬프센터·상태 페이지]

- **Appbot**: 상태 페이지에 2015년부터 날짜별 한 줄 로그. 원인을 플랫폼 쪽으로 귀속 — "Apple reviews delayed by Apple."(2023-07-28), "Google Play reviews were delayed. We found the issue and resolved." 지연 기대치를 미리 공개: Apple 약 48시간 모더레이션, Google 공개 리뷰 24시간, "Apple releases reviews in batches every 3-4 hours". Console 연결 후 앱마다 **Authenticated 배지**, 실패 시 "try again in 24 hours". 연결 만료 메일 알림은 문서에 없음 [미확인].
- **AppFollow**: Statuspage 기반 상태 페이지, 컴포넌트를 **소스 × 기능**(App Store/Google Play 각각 Ratings·Reviews·Reply·ASO·Rankings·Data Source Connection)으로 분리, 이메일·Slack·RSS 구독. 2026-11-18 "App Store connections were disrupted by an Apple-side outage", 11-16 "Google Play ranking data was delayed after a change on Google Play's side". 2022-07 "Delays in reviews collection" 사례는 Investigating → Identified → Monitoring(유료 고객 우선 복구) → Resolved 단계로 두 달 넘게 공개. 헬프센터 본문은 403으로 못 열어 갱신 주기(8시간 등)는 [미확인].
- **공통 패턴 → fixly 문구 설계** [제안]: ① 소스별 상태 칩 "Google Play · 정상 · 마지막 동기화 12분 전" / "App Store · 지연 · 마지막 성공 11-23 18:09" ② 원인 귀속 한 줄(스토어 측 / fixly 수집기 / 브라우저 저장 공간 — 사용자가 기다릴지 조치할지 결정 가능) ③ 기대치 선공지("Google 공개 리뷰는 작성 후 약 24시간, Apple은 최대 48시간 뒤 피드에 나타납니다") ④ 부분 복구 표시 ⑤ 행동 버튼 동봉 [지금 재시도] [CSV로 가져오기] [진단 보기].

### 2-6. fixly 현재 상태 대조 [코드]

| 항목 | fixly VER9 지금 | 위 패턴과의 차이 |
|---|---|---|
| 수집 실패 알림 | `recollect()`가 `/api/collect` 실패 시 토스트 한 줄(`e.message`). 파일로 열면 "서버 주소로 열어 주세요" | 상태(성공/부분/실패)·마지막 성공 시각·원인이 **어디에도 남지 않음**(P7 없음). 토스트는 사라져서 나중에 모름 |
| 0건 vs 실패 구분 | 수집 0건이면 "기간 동안 올라온 리뷰가 없어요 · 수집 기간을 늘려 보세요" | 안내는 있으나 **라이브러리가 실패를 0건으로 돌려주면 구분 못 함**(G2·G10). 서버 `collect.mjs`가 `{status, fetched, expected}`를 돌려줘야 함 |
| 재시도·백오프 | 없음(서버 쪽 `collect.mjs`는 라이브러리 기본값) | P1·P2 없음 |
| 중복 제거 | `addReviews()`가 `reviewId`로 `seen` 체크, 날짜 `isNaN`·빈 텍스트는 건너뜀 | **P4 충족.** 수정된 리뷰 갱신은 없음(건너뜀) |
| 스키마 검증 | 날짜 유효성·텍스트 유무만 | 별점 범위·필드 타입 검사 없음(P6 일부). 격리 목록 없음(P3) |
| 저장 실패 | `persist()` = `try{setItem}catch(e){}` → **조용히 삼킴** | S1·S2 그대로 노출. 용량 초과 시 작업 손실을 사용자가 모름 |
| 버전 불일치 | `load()`에서 `o.v!==17`이면 `seed()`로 **말없이 초기화** | S4의 "백업 후 마이그레이션 또는 확인 창" 없음 |
| JSON 손상 | `load()` try/catch → `seed()` | 복원은 되지만 **손상본 보존·백업 키 없음**(S3) |
| 통계 분모 0 | `pct()`는 null이면 "–", `statCard`는 `o.n`이 0이면 "-", `medianOf`는 `isFinite` 필터 | **S5 충족** |
| 타임존 | 리뷰 `ts`를 `new Date(x.iso).getTime()`으로 저장, 일 버킷은 브라우저 로컬 날짜 | Apple `-07:00` 데이터가 들어오면 KST 기준 날짜가 밀릴 수 있음(S7). 지금 예시 데이터는 Google만이라 드러나지 않음 |
| CSV | `"﻿"` BOM 붙임, 따옴표 escape | **S9 BOM 충족.** 수식 주입(`=`로 시작하는 리뷰) 방어는 없음 |
| XLSX | 라이브러리 없이 직접 생성(압축 안 함), 숫자/문자 셀 구분 | 데모 규모에선 문제 없음. 1만 행 넘으면 S10 |
| 첨부 양식 오류 | "'내용' 칸이 있는 줄을 찾지 못했어요 · 양식을 내려받아 써 주세요", "파일에 VOC가 없어요", "엑셀 파일이 아니에요", "이 브라우저는 엑셀을 읽지 못해요 · CSV로" | **잘 돼 있음.** 단 토스트가 아니라 연동 창 안 자리에 남는지는 확인 필요 |
| 다중 탭 | 없음 | S11. 데모 생략 가능 |

### 2-7. 우선순위 — 3일 뒤 데모 vs 실제 배포 [제안]

| 우선 | 항목 | 3일 데모(최소) | 실제 배포(추가) | 근거 |
|---|---|---|---|---|
| P0 | 실패 ≠ 0건 구분 | 서버 응답을 `{status: ok/partial/failed, fetched, error}`로, 예외 삼키지 않기, 호출 타임아웃 | 소스별 `lastSuccessAt`, 신선도 규칙(24h warn/48h error, 0건 3회 warn) + 알림 | G2·G10·P7 |
| P0 | review_id upsert | 이미 있음(`addReviews`) | DB `ON CONFLICT DO UPDATE`, 수정 리뷰 갱신 | G8·P4 |
| P0 | localStorage 방어 | `storageAvailable()`, `persist()` 실패 시 화면 고정 경고 + 용량 % 표시 | IndexedDB/서버 저장, raw 별도 보관 | S1·S2 |
| P0 | 통계 NaN/0분모/빈 기간 | 분모 0은 이미 "–". 빈 기간 축 선생성과 빈 상태 카드 확인 | 집계 단위 테스트(0건·1건·경계일) | S5·S6 |
| P1 | 429/503 백오프 + 간격 | 서버 `collect.mjs`에 요청 간 ≥1초, 429/503 3회 지수 백오프, 404 중단 | 소스별 서킷 브레이커, 재시도 예산 | G1·P1·P2 |
| P1 | 타임존 고정 | 저장 UTC ISO, 버킷 KST 고정, 차트에 "KST" 표기 | 다중 타임존 | G9·S7 |
| P1 | 스키마 검증 + 격리 | 별점 1~5·날짜·reviewId 검사 → 실패분 격리 카운트 | dbt/GE식 테스트, `mostly` 임계치 | P3·P6 |
| P1 | 상태 UI | 리뷰확인 상단에 소스별 칩(정상/지연/실패 + 마지막 성공 시각) + 원인 한 줄 + [재시도][CSV 가져오기] | 상태 페이지·메일/슬랙 알림 | 2-5 |
| P1 | CSV | BOM 이미 있음. 수식 주입 escape 추가 | XLSX Worker, 대용량은 CSV | S9·S10 |
| P2 | 스키마 버전/마이그레이션 | `load()`에서 버전 다르면 **백업 키에 복사 후** 초기화 + "이전 데이터를 백업했어요" 안내 | `migrations` 체인, 상위 버전 데이터 쓰기 금지, `classifierVersion` | S4 |
| P2 | 수동 CSV 가져오기 | 이미 있는 첨부하기에 Play Console CSV(UTF-16 가능성) 인식 추가 | App Store Connect API(JWT ES256·20분·429 큐) | 2-1·2-2·P9 |
| P2 | 라이브러리 고정 | 버전 pin(Python 1.2.7), 데모 전 스모크 테스트 | 업그레이드 전 회귀 테스트, raw 재해석 | G3·P10 |
| P3 | 국가/언어 검증 | `lang='ko', country='kr'` 기본 | 다국가·중복 제거 | G5 |
| P3 | 다중 탭 | 생략 | `storage` 이벤트 재로드, 낙관적 잠금 | S11 |

## 3. 모니터링 — 어떻게 하는 것이고, fixly에 무엇을 붙일 수 있나

### 3-1. 모니터링의 기본 [사실, Google SRE Book·Workbook, OpenTelemetry, Grafana, Datadog, Kubernetes, healthchecks.io]

**로그 · 지표 · 추적(Logs / Metrics / Traces)**
- OpenTelemetry 정의: Traces = "The path of a request through your application", Metrics = "A measurement captured at runtime", Logs = "A recording of an event". Grafana: "Metrics tell you something is wrong / Logs tell you what happened / Traces tell you where it happened".
- Google SRE Workbook 4장: 알림·대시보드는 보통 지표 기반, 근본 원인 추적은 로그. 지표는 "much less granular information, but in near real time", 비긴급 리포트엔 로그가 더 정확. 드문 이벤트도 카운터로 올려 지표로 알림.
- fixly 번역: 수집기 실행 1회 = 로그 1건(run) + 카운터 몇 개(rows_in/rows_out/errors) + (LLM 도입 시) 분류 호출 1건당 trace. 지금 단계에선 **표 하나(run_log)** 가 세 역할을 겸할 수 있다.

**네 가지 황금 신호 / RED / USE**
- SRE Book 6장: Latency(처리 시간) · Traffic(요청량) · Errors(실패율) · Saturation(얼마나 찼나, "many systems degrade in performance before they achieve 100% utilization"). 화이트박스(내부 지표) vs 블랙박스(사용자처럼 밖에서 테스트). **"Every page should be actionable"**, 증상과 원인 구분이 가장 중요.
- RED(Rate·Errors·Duration)는 요청 기반 서비스용, USE(Utilization·Saturation·Errors)는 리소스용.
- fixly 매핑: RED → 분류 API/LLM 호출(호출 수·실패율·지연), USE → 수집기 큐 길이·브라우저 저장 용량·스토어 API 쿼터 잔량.

**SLI / SLO / 에러 버짓**
- SRE Book 4장: SLI는 "a carefully defined quantitative measure", SLO는 그 목표치. 데이터 파이프라인은 "throughput and end-to-end latency", 모든 시스템은 "correctness". 100% 준수는 "unrealistic and undesirable" → 에러 버짓을 두고 일·주 단위로 추적. 원칙: "Don't pick a target based on current performance", "Have as few SLOs as possible", "Perfection can wait".
- Workbook 2장 파이프라인 SLI 메뉴: **Freshness**("the proportion of the data that was updated more recently than some time threshold"), **Correctness**, **Coverage**(배치가 목표량 이상 처리한 비율). 첫 SLI는 로그처럼 공수 적은 것으로, "the most important goal is to get something in place and measured", 초기엔 매달 SLO 재검토.
- Workbook 13장 데이터 파이프라인: Freshness SLO 형식 "X% of data processed in Y [minutes]", 정답 없을 땐 **golden data**로 비교, "Stale data is almost always better than incorrect data", 실패 원인은 "data delay and data corruption"이 가장 흔함, 장애 후 MTTD·MTTR 추적, "Alerting on the symptom (versus the cause)", 알림마다 플레이북.

**알림 규칙과 임계치**
- Workbook 5장: 알림 품질 = Precision·Recall·Detection time·Reset time. 단순 임계치 → 창 확대 → 지속시간 → burn rate → **다중 창·다중 burn rate(권장)**. 99.9% SLO/30일 기준 burn rate 1=30일, 10=3일, 1000=43분. 권장: Page 1h/5m burn 14.4, Page 6h/30m burn 6, Ticket 3d/6h burn 1.
- Datadog 모니터: Alert threshold(필수)·Warning threshold·Recovery threshold, 평가 창 5분/15분/1시간/커스텀, **No-data 알림 "useful if you expect a metric to always be reporting data"** → 스케줄 수집기에 그대로 해당.
- Grafana Alerting: pending period("prevent unnecessary notifications caused by temporary issues"), keep firing for(깜빡임 방지), 상태 Normal/Pending/Alerting/Recovering/No Data/Error.
- Workbook 4장: 심각도 분류(1시간 낮은 오류율 → 티켓, 100% 오류 → 즉시), 알림 로직도 테스트("very likely that your alerting rules will not fire for months or years").

**헬스 체크 / 하트비트("마지막 성공 실행")**
- Kubernetes probe: Liveness(재시작 판단) · Readiness(트래픽 받을 준비) · Startup.
- 배치·크론용 하트비트(Dead man's switch): healthchecks.io — 작업 **성공 시** 고유 URL에 HTTP ping, period+grace 초과 시 Down → 알림(메일·웹훅·Slack 등), `/start`로 실행 시간 측정, `/fail`로 명시적 실패. 상태 New/Up/Late/Down/Paused.
- 핵심: **성공했을 때만 신호를 보내야** 수집기가 죽어 조용해진 상황을 잡는다(실패 로그 기반 알림만으론 못 잡음).

**대시보드**: Workbook 4장 — SLI 지표를 랜딩 페이지 상단에 "prominently", 버전·설정 **변경 자체도 모니터링**, 의존성(스토어 API) 응답도.

**스케줄 수집기 모니터의 모양** (Workbook 2·13장, Datadog no-data, healthchecks 종합)

| 항목 | 지표 | 계산 | 알림 예 |
|---|---|---|---|
| Heartbeat | last_success_at | 성공 종료 시각 | now − last_success_at > 2×주기 |
| 성공률 | success / runs | 7일 롤링 | < 95% (티켓) |
| 소요시간 | duration p50/p95 | start/finish 차 | p95 > 평소 2배 |
| Rows in/out | fetched · inserted(new) · deduped · rejected | run별 카운터 | fetched=0 N회 연속, rejected 급등 |
| Freshness | now − max(review_posted_at) | 가장 최근 리뷰 나이 | > 24h |
| Coverage | 처리된 스토어/앱 ÷ 대상 | run별 | < 100% |
| Correctness | 샘플 재조회 일치율 | golden data 비교 | 불일치 발견 시 |

### 3-2. VOC→티켓 도구 고유의 운영 지표 [사실, Zendesk·Intercom·Linear 문서, Anthropic 티켓 라우팅 가이드]

| 지표 | 정의 | 근거 |
|---|---|---|
| Freshness | now − 최신 리뷰 게시 시각 | Workbook 2장 |
| Unclassified % | 규칙 미매칭 ÷ 전체 | Zendesk intelligent triage는 분류 필드마다 신뢰도(High/Medium/Low)를 두고 "What is the highest level of confidence needed for the workflow to be effective?"를 먼저 정하라고 권고 |

### 3-4. 분류 작업의 "AI 모니터링" — 정답이 없을 때 품질을 어떻게 재나 [사실, Zendesk·Anthropic 가이드·Evidently·논문]

1. **샘플링 + 사람 검수**: Zendesk(수정된 티켓 리포트, 2주 샘플), Langfuse/LangSmith annotation queue, Braintrust 샘플링(대량 1~10%, 소량 50~100%). fixly 규모(월 100~2,000건)면 10~20% 또는 **저신뢰도 전건** 검수가 현실적.
2. **규칙과의 일치율**: 기존 키워드 규칙을 "약한 정답"으로 두고 LLM 라벨과 일치율 추적. Anthropic 가이드 "Classification consistency… 95 percent or higher"(표준 입력 세트 주기 테스트)를 변형.
3. **라벨 분포 드리프트**: Evidently — 범주형은 참조 ≤1000이면 chi-squared(p≤0.05), >1000이면 Jensen-Shannon(≥0.1). fixly는 주간 라벨 분포 vs 지난 4주. 단 실제 VOC 급증과 모델 드리프트를 구분하려면 규칙 라벨 분포도 같이 비교.
4. **신뢰도 보정**: Tian et al. 2023 — 모델이 말로 낸 확신도("verbalized confidence")가 내부 확률보다 보정이 잘 됨(ChatGPT·GPT-4·Claude). 출력에 `confidence`를 넣고 검수 결과로 구간별 정답률을 그려 임계치(예: 70 미만은 사람 검토)를 정한다.
5. **카나리 프롬프트(golden set)**: 고정 리뷰 30~50건을 매일 1회 분류해 결과가 바뀌면 알림(모델/프롬프트 변경 탐지). Workbook 13장 golden data + Anthropic "standardized inputs".
6. **LLM 판정자 주의**: Zheng et al. 2023 — GPT-4급 판정자는 사람과 80% 이상 일치하지만 위치·장황함·자기 선호 편향. Anthropic: "Code-based grading: Fastest and most reliable… Human grading: Most flexible… Avoid if possible… LLM-based grading: Fast and flexible… Test to ensure reliability first", 판정 모델은 생성 모델과 다르게.

**분류 1건당 기록할 것**: review_id · 입력 해시·길이 · model/version · prompt_name/version · output_label · confidence · reason(한 문장) · schema_valid · stop_reason · refusal(거절은 오분류로 계산) · latency · input/output/cache 토큰 · cost_usd · rule_label · agrees_with_rule · reviewer_label · overridden_at(원본 예측 보존) · batch 여부.

**프롬프트 버전과 연결**: 프롬프트를 코드와 분리해 버전·라벨 관리, generation에 연결 → 버전별 cost/latency/score 비교(Langfuse). 버전 변경 = 모니터링 신호(Workbook 4장 "Intended changes"). 변경 시 카나리 세트 재실행 → 일치율 하락이면 롤백.

**비용 통제 레버**: ① Prompt caching(시스템 프롬프트 ≥ 최소 길이, 읽기 0.1×) ② Batch API(50% 할인, 24시간) ③ 저가 모델 먼저(Anthropic 가이드 "Haiku 5.5… suits ticket routing"), 실패분만 상위 모델 ④ `max_tokens` 256, reason 한 문장(출력 토큰이 입력의 5배 가격).

### 3-5. fixly 적용

**(a) 지금 프로토타입(LLM 없음, 데모까지 3일)** — 외부 서비스 없이 "모니터링이 있다"를 화면과 데이터로 증명 [제안]
- **계산할 것(기존 데이터로)**: ① `collector_runs`(run_id, started_at, finished_at, status, rows_fetched, rows_new, rows_rejected, error_msg) → 7일 성공률·소요시간·rows in/out ② Freshness = now − 최신 리뷰 시각, Staleness = now − 마지막 성공 수집 ③ 미분류 %, multi-hit %, 규칙별 적중 수(어떤 규칙이 죽었는지) ④ 수정률: 라벨 수정 이벤트를 `label_changes`(ticket_id, from, to, by, at)로 → 전체·규칙별 ⑤ 급증: 일별 티켓 수 ≥ 지난 7일 평균 ×2 ⑥ 사이클 타임: 생성→배정, 생성→완료.
- **화면**: 통계자료 상단 한 줄 상태 띠 — 마지막 성공 수집(OK/LATE/DOWN) · 신선도 · 미분류 % · 오늘 수정률 · 7일 성공률. 아래에 일별 수집 vs 티켓 생성, 라벨 분포 추이(주간), 규칙별 적중·수정률 표.
- **알림 3개만**("Every page should be actionable"): DOWN(마지막 성공 후 2×주기) · 미분류 % > 30% 또는 fetched=0 3회 연속 · 특정 라벨 일 건수 ≥ 7일 평균 ×2. 채널 Slack 웹훅 1개. 가능하면 성공 종료 시 healthchecks.io 하트비트 핑 1줄.
- **발표 멘트 근거**: 황금 신호 4개를 수집기 관점(Traffic=수집 건수, Errors=실패율, Latency=실행시간, Saturation=API 쿼터)으로 번역했고, 파이프라인 SLI(Freshness/Correctness/Coverage)는 SRE Workbook 2장 정의를 따랐다.

**(b) 소규모 회사 배포, LLM 분류, 월 100~2,000건** [제안·산식]
- **추천: Langfuse**(Cloud Hobby → 필요시 셀프호스트). Anthropic 공식 destination(코드 변경 없이 Console에서 연결), 프롬프트 버전↔트레이스, annotation queue, LLM 판정, 알림까지 무료 범위, MIT. 차선: Phoenix 셀프호스트(알림 없음), Datadog Free(이미 Datadog 쓰는 회사). 비용만 보려면 Anthropic Console Usage/Cost + Analytics API로 충분.
- **비용 산식**(가정: 시스템 프롬프트 1,500토큰, 리뷰 500토큰, 출력 80토큰, 월 2,000건. 한국어 토큰 비율은 [미확인]이라 여유 있게):
  - Haiku 5.5(입력 $0.10/M, 출력 $0.50/M, 캐시 읽기 $0.01/M): 캐시 없음 2,000 × $0.00024 = **$0.48/월** · 시스템 프롬프트 캐시 시 **$0.21/월** · 배치까지 적용 **≈ $0.11/월**
  - Sonnet 5.5(입력 $2, 출력 $10)로 올려도 **$9.60/월**(캐시 시 $3.90)
  - LLM 판정 20% 샘플(400건, Sonnet): **$2.60/월**
  - 관측 플랫폼: 건당 ≈ 5 units → 10,000 units ≪ Langfuse Hobby 50,000 → **$0**(Helicone 10k req, LangSmith 5k traces, Datadog 40K spans, Braintrust 1GB도 $0)
  - **합계 월 약 $3~13.** 비용은 문제가 아니라 **품질 추적이 핵심**. 비용 모니터링은 "일 $1 초과" 상한 알림 1개로 충분.
- **통합 단계(코드 최소)**: ① Console → Organization settings → OpenTelemetry → Add destination(Langfuse, Metadata only/Full content 선택, admin 권한) ② 앱: `pip install langfuse opentelemetry-instrumentation-anthropic`, `AnthropicInstrumentor().instrument()`, 분류 함수 `@observe()` + `propagate_attributes(session_id=review_id, metadata={prompt_version, rule_label})` (SDK span과 API span 동시 사용 시 토큰 중복 집계 주의) ③ 프롬프트를 Langfuse Prompt Management에 등록해 generation에 연결 ④ 출력은 structured outputs(JSON schema: label enum, confidence int, reason string) → schema_valid 100% 아니면 알림 ⑤ 점수: `agrees_with_rule`(bool), `confidence`(num) 코드로 기록, LLM 판정은 confidence<70 또는 20% 샘플, annotation queue에 저신뢰도 주 20건 → CX 담당 라벨링 ⑥ 알림 2개: 1일 cost > $1 · `agrees_with_rule` 1일 평균 < 0.8 또는 generation 0건(no-data) ⑦ 월 1회 Console Cost와 Langfuse 추정 비용 대조 ⑧ 비용 레버 순서: 캐시(`cache_read_input_tokens`가 0이면 실패) → 밤 수집분 Batch → 저신뢰도만 Sonnet 재분류 → `max_tokens` 256.
- 멘토 메모의 "제공된 AI 기반 모니터링 서비스"가 캠프 지정 서비스라면 위 표의 해당 열을 쓰면 되고, 지정이 없다면 Langfuse가 무료·오픈소스·Anthropic/OpenAI 양쪽 공식 목록 포함이라 설명하기 가장 쉽다.
